# 按排期和页面交付推进

本次截图是 2026-10-08 至 12-31 的 W1–W13 排期。W2 为 10/12–10/16；采用 10/13 rev988 快照抽取的 [W2工作包导航](../assets/w2-baseline.json)。导航包含38项，P0为24、P1为14：服务管理10、价格维护18、基础配置9、系统配置与基础数据1。它不表示这些页面目前均已交付。

后续运行先确认本轮排期版本和选定周列，不根据系统日期猜列、不把 W2 数据套到 W3。若只能用截图或旧快照，声明来源时间；不擅自新增确定日、负责人或交付承诺。

## 阶段含义

| 原排期标记 | 本任务如何处理 |
| --- | --- |
| UI/开 | UI设计与开发并行；已交付页面即可进行通用审查和交互测试 |
| 需 | 需求与判据准备；不计入本周已交付业务 UI 执行数 |
| 开、测 | 按本列实际约定推进；原图例的默认周三提测不能移用到 UI/开 |
| 测／验／上线 | 对照本周实际范围和所需环境，分别记录测试、验收、上线状态 |

用户原安排为“当天输出前端页面UI规范审查与修改清单，本周正式全面介入UI与交互”。10/13聊天中的“当天”是历史日期；后续直接按本轮日期输出，不误写为10/13。

## 可持续执行顺序

1. 每批先取得实际交付页面／入口、运行基线、适用规范及基本可复现数据。先处理已交付 P0、阻塞操作和影响多页的公共问题，再处理 P1 和专项缺口。排期优先级与缺陷等级分别保留。
2. 在已交付页面上先完成规范明确的视觉与操作检查，同批输出问题清单。没有专项设计时仍可测已明确步骤；缺专项判据的分支留待裁决。
3. 开发交付新页面、状态样例或修复 Build 后补测相应项，更新覆盖和问题状态，保留前一轮证据。
4. 周内／周末汇总实际执行页面、已关闭问题、剩余受阻、所需交付条件。若没有明确逐日节点，只列触发条件和下一步，不编造固定星期安排。

## 最小执行跟踪

在现有“范围与依据”中按工作包保留以下必要字段；复杂开发管理表仅在用户另有要求时增加：

`周期｜工作包ID/源序号/源行｜阶段｜排期优先级｜PRD/采纳设计版本｜实际入口｜Build/dirty指纹｜页面交付状态｜UI与交互覆盖｜关联用例/问题｜缺条件｜下一步｜已明确负责人`

负责人未确认时写“待确认”，不从历史聊天推断。入口状态分为“已确认可测”“部分可测”“未取得入口”“本期排除”；排除要有来源。

工作包完成度由其业务页面的适用检查决定。公共组件问题可以关联38项潜在影响，但不能因此算38个工作包已测；缺入口也不能用费用项、Zone或运单模板替代服务单元等其他业务对象。

业务候选每包两条，共76条，是旧工作簿的初始框架。接到页面后按具体交互细化，数量可变，保持原编号映射与修订原因，不强求固定数量。
