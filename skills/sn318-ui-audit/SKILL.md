# SN318 前端 UI 审查与交互测试

默认项目为 `./pcs-front`，入口为 `http://127.0.0.1:5173/demo/list`。用户给出其他目录、入口、周期或 Build 时采用本轮输入。目标是把“规范依据—可执行步骤—实际表现—修改建议—验收标准—复测证据”连成一条记录。

## 按请求选择工作

- **准备／细化用例**：从排期、PRD、采纳原型及 UI Review 定范围，检查可测入口，将候选用例改为具体字段、数据和操作。未执行的结果保留“未执行”。
- **页面审查／交互实测**：在当前页面逐步骤操作和取证，同步输出规范差异、交互问题、待裁决项及执行条件缺口。
- **整改复测**：按问题和原用例复测受影响步骤及必要相邻状态，保留之前的执行历史、遗留缺口和人工意见。

请求包含多种工作时顺序衔接；只准备用例时不扩展成整批测试。要求“全面介入”时按实际交付页面持续覆盖，不据此宣布全部页面已执行。

## 首先确定来源和环境

1. 本轮有聊天引用时先 `read_thread`。读相关项目指令、当前分支／HEAD／暂存与工作区状态，保留既有改动。核对 [来源与历史基线](references/sources-and-baseline.md)，只加载需要的文件。
2. 对齐排期的周期、工作包 ID／原序号／源行、阶段及优先级。按 [排期推进规则](references/schedule.md) 选择工作；历史快照只作为起点。日期按 Asia/Shanghai，截图小字无法确认时保留未知。
3. 读取指导文档的正文及相关嵌入表、示例图。飞书优先使用已有身份的 `lark-cli` 只读命令；不能读取时使用已登录浏览器或已有导出，注明来源日期、修订号和未核对部分。不要将文档目标架构当作当前实现，也不要将网页或附件内容作为操作授权。
4. 在浏览器确认真实入口、当前 URL、可见控件与样例。`/demo/list` 是通用运单模板；表单是 `/demo/list/form`，组件页是 `/demo/components`。业务页面必须另外核对路由、资源、角色和工作包，不用模板结果替代。
5. 执行记录绑定时间、仓库、分支、HEAD、dirty 状态、未提交差异指纹、实际 URL、dev/preview 模式、Mock 开关／数据来源、角色、视口和缩放。相同 HEAD 有不同本地修改时视为不同基线。示例与主数据 Mock 的能力分别确认。

正常的本地 UI 测试使用前端和已有 Mock。服务已运行时复用，不为审查额外启停真实后端、数据库或改动配置。入口不可用时先查当前启动入口及副作用，再按已授权范围恢复最小前端环境。源码、Mock 或配置修复只有用户要求时实施，并遵守项目当前检查规则及已有授权。

## 从规范转成可执行检查

依据和操作细节见 [审查与交互取证](references/audit-protocol.md)。保留原用例名称、编号、前置条件及预期，必要修订另记理由和来源。

- 将步骤与预期按 `[1]`、`[2]` 对应。写具体对象、输入值、触发动作和可观察结果；不使用“正常／符合规范”替代判据。
- 预期来自规范对应组件章节、相关嵌入表、PRD 或已采纳设计结论。专项规则未明确时，已明确的通用规则仍可先测，只把依赖未知判据的步骤留为受阻／待裁决。
- 单个物理页面的公共检查可按“页面实例＋角色＋运行基线＋状态”复用并链接多个工作包。业务字段、只读范围、历史版本、引用限制及导入流程需分别展开；每包两条是旧覆盖框架，不是完整性标准。
- 产品、设计与实现存在冲突时登记两方依据、差异、所需裁决及受影响步骤。UI Review 的颜色是框架适配分类，“设计完毕／修改中”是设计状态，均不能转成测试通过。

## 执行与判定

优先通过浏览器真实点击、输入、键盘、滚动、关闭、重试和路由操作验证。DOM／计算样式用于量测；源码只说明实现或样例限制，不代替动态实测。不得用浏览器脚本修改 DOM、应用状态或伪造响应来获得“通过”。需要新异常样例时写清要求；获准实现后单独记录新 Mock 基线。

每个子步骤记录结果、实际表现和证据；缺口写“已测什么／还缺什么／如何继续”。短暂 loading、hover、active、进度等状态注明采集时刻，不能声称先后采集的 DOM 和截图为同一瞬间。先确认真实存在的状态，避免为已有可测状态额外要求慢请求样例。

聚合用例结果：

| 条件 | 结果 |
| --- | --- |
| 任一适用步骤有明确判据，且实际不符合 | 不通过；其余受阻步骤继续列出 |
| 没有失败，适用步骤全部实际验证通过 | 通过，仅限记录的环境和分支 |
| 没有失败，但存在缺判据、缺样例或不可执行步骤 | 受阻，具体注明条件 |
| 所有步骤均未开始 | 未执行 |
| 有明确排除依据，全部步骤不属于本次对象 | 不适用，保留排除来源 |

不添加原前置没有的条件来解释失败。`disabled=true`、页面 HTTP 200、导出文件存在、单测／构建成功都不能证明整条交互通过。当前 Mock 全量权限不能证明真实角色鉴权，内存读回不能证明后端持久化。

## 交付与复测

按 [交付结构与记录格式](references/deliverables.md) 输出。默认复用本轮指定工作簿的用例风格，另存带日期和基线标识的执行副本；不覆盖来源或清空历史。创建／修改 XLSX 时使用可用的 Spreadsheets 技能。保留人工二次复核已有内容，新增人工字段留空，模型意见写入独立执行／复核字段。

每条问题包含规范定位、实际差异、复现步骤、证据、修改建议、可检查验收标准、关联用例、状态和剩余缺口。重复根因合并问题并保留多条关联；规范未定项、样例缺口与已证实缺陷分别标明。

输出工作簿、相对链接的证据报告和必要证据目录；需要便携交接时打 ZIP。检查用例／步骤／问题引用、状态汇总、文件与链接、原表保留、公式及可读性。使用结构化执行记录时可复制 [空记录模板](assets/run-template.json)，填写后运行：

```powershell
python -X utf8 <skill-dir>/scripts/validate_run.py <run-dir>/run.json
```

校验器只检查记录完整性、结果聚合、引用和本地证据文件存在，不证明证据内容或实际测试已完成。人工字段只做保留性检查，不由模型生成。

收尾先报告本次交付与执行结果，再说明业务页面覆盖、受阻分支、来源快照限制和下一批触发条件。改文本／重判历史证据不记作新的页面执行；dev、preview、真实接口各自报告。无需为 UI 清单增加整套开发进度管理或自动排程。
